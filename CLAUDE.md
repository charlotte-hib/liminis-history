# Who Lived When

Spring Boot 4 + Kotlin backend (`backend/`), Next.js 16 frontend (`frontend/`, see `frontend/CLAUDE.md`). Product and design context: `README.md`.

## Local commands

- Java 25 (jenv, `.java-version`) and Node 24 (nvm, `.nvmrc`). The shell's default Node is older: run `source ~/.nvm/nvm.sh && nvm use` in `frontend/` before any npm command.
- Backend: `cd backend && ./gradlew test` / `./gradlew bootRun` (port 8080). Both need Docker Desktop running: the tests start Postgres with Testcontainers, `bootRun` starts the `db` service of `backend/compose.yaml` (Spring Boot's Docker Compose support).
- Workbench (`backend/workbench`, the curator's tools, on the curator's computer only, never in an image): `./gradlew :workbench:bootRun` starts it as a server on `127.0.0.1:8090` (API `api/workbench.yaml`, every request needs the token it writes on each start to `~/.config/who-lived-when/workbench-token`, and a `Host` of `localhost` or `127.0.0.1`); `backend/workbench/wb` (bash, curl, python3) starts its runs, one at a time, and follows them. `wb draft <id>` drafts a story with Claude into `backend/drafts/` (needs `ANTHROPIC_API_KEY`); `wb import` fetches Wikidata's people, their places and occupations, three levels of classes above the occupations, and the intros of their English and French Wikipedia articles into its schema `raw` (its own Flyway migrations, `db/raw`, never dropped), resuming a run that stopped, and refreshes by revision when run again; `wb map` maps the last finished import to rows in schema `dataset` (`db/dataset`, rebuilt on every run): people, their Wikipedia articles, their places with the country each lies in today (Natural Earth's borders, downloaded on the first run into `backend/natural-earth/` and pinned by sha256 in `application.yaml`), and occupations; `wb claims` proposes the facts of the people of the release's moments as claims to review, in schema `curation` (`db/curation`, never dropped: the curator's decisions); `wb queues` shows what waits. Its Postgres is `compose.workbench.yaml` (project `who-lived-when-workbench`, volume `workbench-db-data`), started the same way.
- Database: Postgres 18 (the `db` service in `docker-compose.yml`, image pinned by digest; the tests read their image from it). Schema in SQL migrations, `backend/core/src/main/resources/db/migration`, run by Flyway; Hibernate only validates (`ddl-auto: validate`). Each release is loaded into its own schema, `release_<commit[:12]>` (`APP_RELEASE_ID` from `RELEASE_SHA`), by the last migration, `LoadRelease` (version 999); `release_local` (no id: bootRun, tests, CI) is rebuilt on every start. Never edit an applied migration: add one. Roles: `site_owner` (Flyway, owns the schemas), `site_reader` (the API: select, plus update of person's Wikipedia columns), from `db/roles.sql`.
- Frontend: `cd frontend && npm run lint && npm run build` / `npm run dev` (port 3000).
- API contract: `api/openapi.yaml`, spec first. The backend generates its controller interfaces and models from it (`./gradlew :site:openApiGenerate`, run by every build): change the spec, never the generated code. The frontend's types: `npm run api:types` in `frontend/` regenerates `lib/api-schema.ts` (committed; CI fails when stale), and `lib/api.ts` and `lib/api-browser.ts` call the backend through `openapi-fetch`. Lint: `npx @redocly/cli@2.54.2 lint api/openapi.yaml api/workbench.yaml --config api/redocly.yaml`. The workbench's contract, `api/workbench.yaml`, generates its interfaces the same way (`:workbench:openApiGenerate`). Swagger UI on `bootRun` only: http://localhost:8080/swagger-ui.html.
- API tests: with the backend running (`--app.wikipedia.enrich=false`), `ijhttp --env-file http/http-client.env.json --env local http/api.http` (add `-V baseUrl=http://localhost:<port>` for another port). Never point them at production: only `http/production.http` (read-only GETs, no visitor events) runs there, by `.github/workflows/smoke.yml`.
- Both in Docker: `docker compose up --build`, then http://localhost:3000. Docker Desktop is often not running on this Mac.
- End-to-end (Playwright, against a running site): `cd e2e && npm ci && npm run typecheck && npx playwright test` (`BASE_URL`, default http://localhost:3000). Locally it drives the installed Google Chrome: Playwright's Chromium does not run on macOS 13.

## Production

Merging to `main` deploys. Server details and access are kept out of this public repo: @~/.claude/who-lived-when-ops.md

- **Pipeline** (`.github/workflows/ci.yml`): pull requests run backend tests and frontend lint and build, then the `images` job builds each image once (a one-day artifact) and the API tests (`http/`) and end-to-end tests (`e2e/`) load those exact images; only the first two are required checks. On `main`, the same images are pushed to GHCR (`ghcr.io/charlotte-hib/who-lived-when-{backend,frontend}`, tagged `sha-<commit>`) with signed SLSA provenance and SPDX SBOM attestations. The `deploy` job (environment `production`, `main` only) waits for every test, verifies the provenance, joins the tailnet through Tailscale workload identity federation, and runs `deploy/deploy.sh` over Tailscale SSH. Then `smoke.yml` checks the live site from outside (also daily at 06:17 UTC, address from the repository variable `SITE_URL`); its failure turns the run red but never rolls back. `workflow_dispatch` redeploys `main` by hand.
- **No secrets in GitHub.** Repository variables only. Do not add SSH keys or tokens.
- **Releases**: production serves the private repo `charlotte-hib/who-lived-when-data` (`data/`, cloned at `~/Desktop/who-lived-when-data`), not `sample/`. Its CI starts the public images of the commit in production on the candidate `data/` and probes them; on merge it pushes `data/` as a private OCI artifact, `ghcr.io/charlotte-hib/who-lived-when-release:<data/'s Git tree hash>` (newest 10 kept), and prints the two lines for `release.lock`. Changing `release.lock` is a pull request of its own here. The package grants this repo's Actions read access; the deploy job pulls it with ORAS and pipes it to `deploy.sh`. A format change lands here first (with `sample/`), then in the data repo. Never copy `data/` into this repo.
- **`deploy/deploy.sh`** runs on the server in a clone of this repo: checks out the commit, fills in `db.env` and `db-roles.env` with random passwords where missing, unpacks the release bundle from stdin into `releases/<RELEASE_ID>` (kept: the three most recently deployed, and the current and previous ones), writes the release (commit, image digests and `RELEASE_DIR`) to `.env`, `docker compose up` for `backend` and `frontend`, probes `/` and `/api/search?q=a` (an API path the frontend forwards) through the reverse proxy, and rolls back to `.env.previous` if unhealthy within 3 minutes. Once healthy, it starts or updates Prometheus and Grafana when `grafana.env` exists (adding `COMPOSE_PROFILES=monitoring` to `.env`); a monitoring failure never fails the deploy or rolls it back. Its body is in functions because it rewrites itself through `git checkout`.
- **Compose**: `backend` (no published port, `SPRING_PROFILES_ACTIVE=prod` points it at `db` and moves Actuator, `/actuator/health` and `/actuator/prometheus`, to port 8081, reachable on the Compose network only), `db` (Postgres, no published port, volume `db-data`, 256 MB), `db-roles` (one-shot: creates the roles and sets their passwords on every `up`; `backend` waits for it) and `frontend` on `127.0.0.1:3000`. The release is `RELEASE_DIR` (default `sample/`), mounted read-only at `/app/release` (the image holds no data); the backend keeps the current release schema and the two newest others. Wikipedia enrichment takes about a minute on a new schema. Passwords: `db.env` (`POSTGRES_PASSWORD`, superuser: `db` and `db-roles` only) and `db-roles.env` (`SITE_OWNER_PASSWORD`, `SITE_READER_PASSWORD`: `db-roles` and `backend`), both untracked, next to `.env`, mode 600, made by `deploy.sh`; locally `db/defaults.env` and `db/roles.env` apply. Postgres only reads the superuser's password when it creates its data directory: if `db.env` is ever lost, remove the `db-data` volume too (nothing in it needs keeping). Change a role's password in `db-roles.env`, then redeploy.
- **Monitoring** (`monitoring/`, Compose profile `monitoring`, off in CI and by default): `prometheus` (30 days or 1 GB) and `grafana` on `127.0.0.1:3001` only, never in the Caddy snippet, with named volumes `prometheus-data` and `grafana-data`. Grafana's admin password comes from `grafana.env` (`GF_SECURITY_ADMIN_PASSWORD=...`, untracked, next to `.env`), which can also override `monitoring/grafana/defaults.env` (e.g. `GF_SERVER_ROOT_URL`); keep overridable settings there, not under `environment:`, which wins over both. Datasource, dashboards and alerting are provisioned from the repo: change the JSON in `monitoring/grafana/dashboards/` and the YAML in `monitoring/grafana/provisioning/`, not in the UI. One alert: API traffic above 1 request a second for 10 minutes, emailed to `ALERT_EMAIL` through the `GF_SMTP_*` settings in `grafana.env`; `defaults.env` holds a placeholder address so Grafana starts without them. Visitor events (`POST /api/events`, `frontend/lib/analytics.ts`, `VisitorEvents.kt`) carry only labels from closed sets: no ids, IPs, user agents or URLs.
- **Rate limit** (`frontend/proxy.ts`, `frontend/lib/rate-limit.ts`): per visitor, keyed on the `X-Forwarded-For` Caddy sets (IPv6 by /64), in the frontend's memory. Requests without it and from private addresses are never limited, so CI, local runs and the deploy probe are not; keep Caddy in front of the frontend.
- Keep server details (addresses, hostnames, users, firewall, other sites) and personal details out of tracked files and commit messages, including `README.md` and this file. The server provides the site addresses: its Caddyfile lists them, and `site.env` (untracked, next to `.env`) gives `deploy.sh` the address to probe.
